# 敏感词过滤设计评估

## Goal

评估在 Workers 热路径上做入站敏感词过滤（命中即拒绝、不发上游）的成本与语义。对照 New API 的实现：词表配置 + prompt 命中后上游前拒绝、不影响渠道健康。我们的核心顾虑：proxy 热路径现状是「默认不解析请求体」的零成本形态（入口日志 `[request]` 仅 method/path），敏感词过滤本质要求**每请求解析 body + 全文扫描**——等于把热路径从零 body 解析拉回全量解析。用户明确「要看看成本，毕竟是 worker」。

**本任务交付物是评估报告，不写任何业务代码。** 用户看完报告决定是否立项实施；实施另开子任务挂批次父任务（`10-28-cpa-newapi-adoption-batch`）下。

## 评估问题（报告必须逐项回答）

- **Q1 性能成本测算**：词表规模档位（50 / 500 / 5000 词）× 请求体档位（4KB / 64KB / 1MB）下，朴素逐词 `includes` vs Aho-Corasick 单趟多模匹配的成本对比；Workers CPU 限额下的安全余量结论；词表编译一次 + isolate 内存复用的可行性（照 channel-cooldown 模块级缓存范式）。**必须有可复现的测算方法**（benchmark 脚本或量化推理依据），不许拍脑袋。
- **Q2 词表存储与热更新**：settings 键（走 `loadProxySettingsCached` 30s TTL）vs 专用表；词表规模上限（D1 单行值大小约束）；管理台编辑形态。
- **Q3 匹配域语义**：仅用户消息文本（chat messages / anthropic messages / responses input 三形状）还是含 system/tools 全文？**passthrough 路径不解析 body → 豁免（过滤存在绕过面）还是补充解析（破坏 passthrough 零成本契约）**——两难摆清楚，给建议。
- **Q4 命中行为**：4xx 错误码命名（`ERR_*` 惯例）；必须不计渠道失败/冷却（请求级拒绝）；不进 IP 鉴权失败节流（非鉴权失败）；是否写 usage_logs（可审计 vs 存储/隐私成本）——给建议。
- **Q5 开关与默认行为**：settings 总闸默认关（照 `probe_interval_minutes` 形态 0 = 关）；全关时零额外查询的早退顺序设计。
- **Q6 误杀面**：子串误匹配（短词撞常见字）的缓解手段（最小长度、分词、豁免清单）与如实声明的残余风险。
- **Q7 工作量估算**：人日级 + 任务拆分 + 回滚形状（总闸关闭即回到现行为）。

## 非目标

- 不做出站响应内容过滤（只管入站 prompt）。
- 不做图片/音频内容审核。
- 不接入外部内容安全 API（纯本地词表）。
